## 1. Get a key

No account, no approval step.

```bash
curl -X POST https://api.useroutr.com/v1/sandbox_keys \
  -H "content-type: application/json" \
  -H "idempotency-key: $(uuidgen)" \
  -d '{ "name": "Ada Lovelace", "email": "ada@example.com" }'
```

Keep the `secret_key`. It is shown once. See [Sandbox keys](/guides/sandbox) for
what it can reach and what it cannot.

```bash
export USEROUTR_SECRET_KEY=sk_test_...
```

## 2. Create a funding intent

Server side, always. The browser can complete an intent, never define one.

```ts
import { Useroutr } from "@useroutr/sdk";
import { randomUUID } from "node:crypto";

const useroutr = new Useroutr({ apiKey: process.env.USEROUTR_SECRET_KEY });

const intent = await useroutr.fundingIntents.create(
  {
    amount: { amount: "1.00", asset: "crypto:USDC" },
    destination: {
      rail: "stellar",
      asset: "crypto:USDC",
      target: { kind: "chain_address", address: "G..." },
    },
    reference: "order_8812",
  },
  { idempotencyKey: randomUUID() },
);
```

Every mutating call needs an idempotency key, and you choose it. A retry of your
own logic should reach the same key: a fresh one creates a second intent, which
is the thing idempotency exists to prevent.

## 3. Price it, then accept

```ts
const options = await useroutr.fundingIntents.options(intent.id);
// [{ id: "qt_...", source: { rail, asset }, pay_amount, receive_amount_min, ... }]

const accepted = await useroutr.fundingIntents.accept(intent.id, options[0].id, {
  idempotencyKey: randomUUID(),
});

console.log(accepted.pay_to);
// [{ rail: "stellar", asset: "crypto:USDC", address: "G...", memo: "fi_..." }]
```

Accepting pins the route that was quoted. It is never recomputed: a price your
user agreed to and a route worked out a moment later are not the same promise.

<Warning>
  On a rail that carries a memo, send it. A payment arriving without one cannot
  be matched to an intent, and on most rails it cannot be recovered either.
</Warning>

## 4. Pay it

Send the `pay_amount` to the `pay_to` address on a testnet rail, with the memo
if there is one. On Stellar testnet, a friendbot-funded account and a USDC
trustline is enough.

## 5. Watch it settle

```ts
const events = new EventSource(
  `https://api.useroutr.com/v1/events?funding_intent_id=${intent.id}`,
);

events.addEventListener("funding_intent.transitioned", (e) => {
  console.log(JSON.parse(e.data).status);
  // awaiting_payment -> payment_received -> settling -> settled
});
```

The server owns the state and the stream reports it. Do not rebuild the
lifecycle in your own code: it drifts from the only copy that matters.

Polling `GET /funding_intents/{id}` works if streaming is unavailable. Back off
exponentially rather than at a fixed interval, or a degraded API becomes a
degraded API with a thundering herd.

## What you just proved

A funding intent reached `settled`, which means a **double-entry ledger credit
exists**. Not a transaction hash. A hash is evidence; the credit is completion.
